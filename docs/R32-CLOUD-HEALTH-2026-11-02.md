# R32 素材库体检：让「素材库是否都添加好了」变成用户自己能验的事

## 问题

前面几轮我一直用「我查过了，六个源都在」来回答「素材库是否都添加好了」。这个答案的问题在于：**它依赖我，不依赖用户**。上游改结构、限流、某个源挂掉，我看不到，用户更看不到——只能等界面某天突然变空。

而且这一轮真出过事：`char-db-cn` 悄悄加了 `outfit2` 的 1,320 条，是被我手工比对发现的。如果那天没比对，姿势分类里就会混进一堆动漫衣装。

## 做法

新增 IPC `reference-library:health`，逐源体检，设置页加一张表。

关键设计：**不用 `load()`**。`load()` 里增量源失败会退化成空数组（R17 起的设计，为了一个源坏了不拖垮别的），但那样体检就永远显示「正常但 0 条」，等于自己骗自己。所以另写 `fetchDepthPosesStrict` / `fetchAnimeCostumesStrict`，失败直接抛，把原因带出来。

```ts
async health(): Promise<CloudHealthReport>
```

`CloudSourceHealth` 每行：`key` / `label` / `count` / `status`（ok / empty / error）/ `error` / `durationMs`。

**口径陷阱**：第一版 `totalItems` 把「姿势 1,439 张」和「姿势 288 组」都加了一遍，算出 8,419 条，而分类行加起来是 6,980。真机一跑就露馅了。改成和 `counts` 同一口径——姿势按组算（288），char-db 按 set 拆（hair 306 / outfit 440 / pose 281）。

## 一个绕了很久的坑

CDP 一直连到**残留的旧 Electron 进程**上——端口 9491 上有别的东西在响应 `/json`，页面 href 显示的是项目路径，但实际加载的 `script` 是 `index-B7pd7Z5b.js`，而磁盘上只有 `index-wm-SibVL.js`。表现就是：代码明明改了、bundle 里明明有那段字符串、页面就是不渲染。

排查顺序：查 bundle 内容（有）→ 查 index.html 引用（对）→ 清 Electron 缓存（没用）→ **打印页面实际加载的 script 名（对不上磁盘）**→ 换一个新端口（4507→9513）→ 立刻正常。

**教训**：CDP 端口每次都要换新的，或者先确认 `/json` 里的 target 是自己刚 spawn 的那个进程。只看 href 不够，要看 `document.querySelector("script[src]").getAttribute("src")`。

## 补：抽检图片能不能真的打开

上一版体检只数条数——条数对了不代表图还在。补了「样图」列：每个源均匀抽三张（首、中、尾，`pickSample`），并发验 HTTP 状态。

```
来源        条数    状态   耗时      样图
姿势        1439    正常   2727 ms   抽检 3 张均可打开
服装        1407    正常   2678 ms   抽检 3 张均可打开
人像        1499    正常   2714 ms   抽检 3 张均可打开
二次元换装  1027    正常   2717 ms   抽检 3 张均可打开
深度图      1439    正常   2469 ms   抽检 3 张均可打开
动漫衣装    1320    正常   2448 ms   抽检 3 张均可打开
```

两个工程细节：

1. **抽缩略图不抽原图**。第一版抽原图，六个源各三张，耗时 4.4 秒；换缩略图降到 2.7 秒。验的是「这个源还能不能出图」，不需要拉原图。
2. **`char-db` 的抽检改用 `CHAR_DB_THUMB_BASE`（github raw 的 thumbs）**，不是 `CHAR_DB_IMAGE_BASE`（pages.dev 的 img）。前者跟条目数据同源，后者是独立 CDN，抽前者更能反映「数据源本身是否健康」。

失败时的文案会带状态码，例如「抽检 3 张，1 张打不开：404」。

## 还没做的

- 抽 3 张是抽样，不是全量。全量 8,131 张要跑几分钟且会踩上游限速。
- 没验图片**内容**是否真的是一张图（只看 HTTP 状态）。上游如果把图片换成 404 页面但返回 200，这里看不出来。

## 补二：抽检看 content-type，不只是状态码

只看 HTTP 200 不够：上游把图片换成错误页时，通常还是 200 返回一段 HTML。现在除了状态码还看 `content-type` 是否 `image/*`，不是就判失败并写出实际类型：

```
抽检 3 张，1 张打不开：返回的不是图片（text/html; charset=utf-8）
```

测试 `electron/services/reference-library.test.ts` 加了一例：mock 让图片地址回 `200 + text/html`，断言条目本身 `status === "ok"`（数据读到了）但 `images[0].ok === false` 且 error 含「不是图片」。两条断言分开，是为了区分「数据源挂了」和「图挂了」——它们是两个故障。

「数据显示出来了」和「用户能拿它出图」是两件事。写了 `/tmp/check-sources-usable.mjs`，走真实界面：创作 → 参考卡组合 → 云端图库 → 逐个分类点一张卡 → 读左侧槽位绑定的文字。

## 补四：清理我留下的垃圾（用户指出的）

用户发来一张截图，Dock 里排了一长列无名图标。查下来是我的问题，两个来源：

**一、16 个没退出的 Electron 实例。** 取证脚本 `child.kill("SIGKILL")` 只杀掉了 `node_modules/.bin/electron` 这层 node 包装进程，真正的 Electron 主进程变成孤儿继续跑，每个还带着 GPU/网络/渲染三个子进程。而且它们都占着 `--remote-debugging-port`（9471/9491）——这正是前面那个「CDP 连到旧进程、代码改了页面不更新」的坑的真正原因：端口上同时有三个 Electron 在抢，连到哪个看运气。已全部杀掉。

**二、353 个临时目录，合计 80 GB。** 25 个测试文件用 `mkdtempSync` 建临时目录，95 处调用，只有 6 个文件写了清理。跑几十次测试就积成：

```
vas-job-*      189 个
vas-secret-*    81 个
vas-export-*    81 个
其他             2 个
```

修法：新增 `scripts/clean-tmp.mjs`，`npm test` 改成前后各清一次——

```json
"test": "node scripts/clean-tmp.mjs && npm run rebuild:native:node && vitest run; node scripts/clean-tmp.mjs --all"
"clean:tmp": "node scripts/clean-tmp.mjs"
```

跑前那次只删 5 分钟前的（避免误删并行测试正在用的目录），跑后那次带 `--all` 全清。验证：一次 `npm test` 后残留目录从 32 个降到 0 个。

**没做的**：没有逐个给那 25 个测试文件补 `afterEach` 清理。理由是改 95 处调用容易引入 flaky，而集中式清理一样能达到「跑完不留下东西」，且不侵入测试逻辑。如果以后有人用非 `npm test` 的方式跑 vitest，还是会漏——这一点记在这里。
