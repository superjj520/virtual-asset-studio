# R55 · 竞品拆解：truejpeg.com 的提示词工程

用户给了 https://truejpeg.com/#prompt 说「给你拓展提示词的能力，以及有人超过你的能力了，
看看竞品怎么玩的」。这份是把它的数据层扒开之后的对照，不是看首页猜的。

## 一、它是什么

一句话：**AI 图片 + 完整提示词，点一下复制**。三块：

- `#prompt` 作品墙：144 条，每条一张图配一整段中文提示词，点击复制
- `#generate` 生成器：接第三方闭源模型（OpenAI / Google / ByteDance / xAI / Recraft），
  按张收点数（**1 点 = 0.01 美元**，含税），另有两条 affiliate 外链（Higgsfield、Yir，
  Yir 号称比官方便宜 88%）
- `#other` 占位，写着 In preparation

前端三个数据文件：`works.js`（508 KB，全部作品）、`data.js`（站点信息）、`i18n.js`（三语）。
`works.js` 头一行写着 `// generated by tools/import_export.py, do not edit by hand`——
说明它是从别处（`gallery-export.zip`）批量导出的，不是手工一条条贴的。

## 二、数据结构

每项字段：`id / title / image / thumb / width / height / prompt / negative / params / tags / date / source / ref / post`。

实测：

| 指标 | 值 |
| --- | --- |
| 作品数 | 144 |
| 提示词长度 | 中位 **997 字**，最长 2,540 |
| 段落数 | 中位 **9 段**，范围 0–17 |
| `negative` 字段 | **144 条全空** |
| 标签 | Portrait 128 / Anime 14 / NSFW 11 / Poster 2 |
| 模型 | 多为 `SeeDream 5.0 Pro`，部分 `ref: null` |
| 标题词频 | portrait 141 / fashion 134 / black 21 / floor 18 / street 12 / balcony 12 / mirror 11 / sofa 10 / hotel 10 |

标题几乎全是 `<场景或机位> Fashion Portrait`——**同一个人、换机位、批量出**。
`Sofa / Window / Mirror / Floor / Street / Balcony / Hotel / Bedroom` 各来几条。

## 四、四条真正的差距

### 1. 它把负向要求写在正向段落里（71% 的作品这么做），`negative` 字段一条没用

144 条作品的 `negative` 全是空的。所有「不要墨镜」「避免纸片身材」「不能做成大面积柔光箱效果」
都写在对应段落里，跟着正向描述一起走。

这正好命中我们自己记过的坑：`docs/R54-QWEN-EDIT-WORKFLOW.md` 里写着
**「cfg=1 时反向词不生效」**——Qwen-Image-Edit 的官方工作流就是 cfg 1 + Lightning 4 步。
我们辛苦填的 `negative` 在那条链路上等于没写。

### 2. 「画面质感」独立成段，84% 的作品都有，我们这一块几乎是空的

它写的是：`2000s日系便携CCD极低照度直闪抓拍质感，有限动态范围、轻微柔焦、明显数字噪点与粗颗粒、
黑位压深。暗部带轻微青绿色和灰紫色偏色；直闪区域有轻微高光溢出，但不要过曝。`

我们的 `compilePrompt` 里对应的是 `具体视觉风格：真人电影摄影`——**一句话**。

「像不像 AI 图」八成由这一段决定：噪点、色偏、柔焦、高光溢出、黑位，都是具体可写的东西，
而我们只给了一个形容词。

### 3. 它一句一行，我们全挤在一行

它：9 段，每段独立成段、带中文冒号小标题。
我们：`prompt-compiler.ts:31-33` 是 `modules.map(item => \`${item.label}：${item.value}\`).join("；")`——
13 个模块用分号连成**一整行**。

对 Qwen / Seedream 这类吃长文本的模型，段落边界的意义不只是好看：换行是明确的分段信号，
分号只是标点。我们自己在 R54 里也把「结构化提示词」当卖点讲，但输出是一行。

### 4. 长度差 8 倍，但差的不是字数

它中位 997 字，我们约 120 字（`prompt-compiler.test.ts` 里那条用例整段实测）。

差距不在「写得多」，在于它**每一项都写到了可执行的颗粒度**：

| | 它 | 我们 |
| --- | --- | --- |
| 头发 | 「短 Bob，长度到下巴，头顶圆润顺滑，发尾轻微内扣；额前厚而整齐的长碎齐刘海，接近眼睛上缘」 | 「黑色长发」 |
| 镜头 | 「镜头靠近膝盖前方并略低于人物胸口，焦段约 28mm—35mm，带轻微广角透视」 | 「85mm 头肩肖像」 |
| 光 | 「弱正面直闪从镜头附近打向脸部、腿部和手部，环境光极弱，局部反光要硬而真实」 | 「暖白主光与冷色轮廓光」 |

## 五、我们该学什么、不该学什么

**该学（按性价比排）**：

1. **把 `negative` 的活并回正向段落**——`compilePrompt` 改为「每段末尾附上该段的负向要求」，
   `negative` 只留给全局硬禁（水印、文字）。这一条不改模型、不改工作流，立刻见效。
2. **补一个「画面质感」模块**——CCD 直闪 / 胶片颗粒 / 数码噪点 / 色偏预设化，
   现在 `reference-styles.ts` 有 15 个画风，但没有一个是「质感」维度。
3. **`join("；")` 改成 `join("\n")`**——一行改完，风险最低。
4. **身份锚点后面加一句抗漂移条款**——它在第 1 条里写了
   「即使参考图人物为长发，也必须继续保持固定短 Bob」，只有 2% 的作品有，但这一句正是我们 R20
   花一整轮查出来的漂移根因（提示词自相矛盾）。

**不该学**：

- 它的作品墙是**成品图**（没法当素材用），我们要的是可组合的参考资产，定位不同。
- `source` 字段多半是空的、`ref` 常为 null，说明它的溯源做得没我们细（我们有 sha256 + 权利状态 + 来源 URL）。
- 它没有「同一角色跨图一致性」的机制，靠的是把人物描述抄进每一条提示词；我们有角色档案 + 参考板。

## 六、我打算怎么落地

不进代码之前先给结论，避免又变成「加了一堆字段没人用」：

- 第一步只改 `compilePrompt` 的输出形态（分段 + 段内负向 + 质感模块），
  配一个「同一张卡改前 / 改后」的对照测试，人眼能看出差别再继续。
- 第二步才是「质感预设」进 `reference-styles.ts`，因为要动 UI。
- 竞品那 144 条不抄文案（是人家的作品），只把**结构**当参考。
