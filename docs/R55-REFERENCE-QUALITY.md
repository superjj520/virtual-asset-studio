# R55 · 素材库的质量体检（不只是数条数）

R32 做的「素材库体检」回答的是「七个源还活着吗、各有几条」。这一轮补的是另一半：
**条数涨到 7,924 之后，用户到底能不能用**。

`npm run verify:quality` 会真起应用、把整个目录拉下来，在页面里统计一遍：

| 检查 | 判的是什么 |
| --- | --- |
| 每条都有标题 / 分类 / 缩略图地址 | 有没有 `undefined` 漏进界面 |
| 没有大面积重名 | 下拉里会不会出现几百个一模一样、选不准的选项 |
| 中文检索词都能搜到 | 用户打「站姿」「半身裙」能不能出东西 |
| 英文关键词也能搜 | 服装库的中文名是「象牙白荷叶边针织衫」，用户可能想打 `white` |

## 第一次跑就抓到的事：301 个「短发・标准款」

人像库是「同一个发型的多张样本」——标题就是发型名，所以：

```
短发・标准款                            301 条
中发・标准款                            178 条
中长发・标准款                          140 条
长发・标准款                            136 条
```

而 ComfyUI 的人像节点是靠**标题**当枚举值的。这意味着用户在 1,499 项的下拉里，
会看到 301 个一模一样的「短发・标准款」，选哪个都一样——**根本没法说清自己要哪一张**。

这不是"数量不够"，是**数据到了界面上不可用**。

## 修法：重名的补组内序号

给重名标签补一个组内序号，只出现一次的保持原样（不在界面上无端加后缀）：

```
短发・标准款 · 1
短发・标准款 · 2
...
中发・标准款 · 1
```

**同一份数据在仓库里有两套实现**，两边都得改，否则用户在 App 里和 ComfyUI 里看到的
两个下拉对不上：

- `electron/services/reference-library.ts` 的 `portraitItems`（App 侧）
- `comfyui-vas-nodes/vas_data.py` 的 `dedupe_labels`（节点包侧）

`dedupe_labels` 抽成了纯函数，`contract_test.py` 里加了断言：去重后无重名、
按出现顺序编号、唯一标签不加后缀、**不能丢条目**（去重不是过滤）。

## 顺带补：英文关键词进搜索语料

服装库每条都带一个 `关键词` 字段（`ivory frill knit denim mini skirt coat socks white sneakers`），
之前只把中文 `标签` 放进 tags，英文是丢掉的。用户习惯打 `white shirt`，
而中文名是「象牙白荷叶边针织衫」——只靠中文名什么都搜不到。

补进 tags 之后：

| 词 | 修之前 | 修之后 |
| --- | --- | --- |
| `white` | 0 | 728 |
| `denim` | 0 | 301 |
| `skirt` | 0 | 984 |

## 修完之后

重名从「最多一组 301 条」降到「最多一组 13 条」（那是服装库里几条同款不同色的套装，
标题本来就一样，13 条在可接受范围内）。

真 ComfyUI 里复核：人像 1,499 项 / 服装 1,407 项 / 姿势 1,439 项，**重名全部为 0**。

## 一个不打算修的

搜「白衬衫」是 0 条，「校服」也是 0 条。

不是检索坏了——是上游把衣服叫「针织衫」「开衫」「吊带衫」，全库 1,407 条里
没有一条含「白衬衫」这三个字连写；「校服」在这个库里叫「制服」（41 条）。

这类"词对不上"的问题在数据侧，改我们的代码没意义。体检脚本的断言改成用**库里真实存在的词**
（`衬衫` 139 条、`半身裙` 477 条、`牛仔` 182 条……），而不是我凭印象觉得应该有的词——
第一次写这版脚本时就是拿「白衬衫」当断言，结果红了半天才发现是断言错了不是产品坏了。
